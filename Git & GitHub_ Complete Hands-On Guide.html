Module 1Version Control System (VCS) Basics

🧠 In 3 lines
WhatA tool that remembers every version of your files.
WhyUndo mistakes and work in a team without overwriting each other.
HowYou save snapshots called commits, each with a message, and can go back any time.

A VCS tracks changes to files over time. It lets you see history (who, what, when, why), go back when something breaks, work in a team without overwriting each other, and build features in isolation with branches.

Without it you get report_final.docx, report_final_v2.docx, report_final_REAL.docx. A VCS replaces that with one searchable history.

BranchAn independent line of work
RemoteA copy of the repo on a server (GitHub)
CloneA full copy of a remote repo on your PC

What is "origin"? (simple words)

🧠 In 3 lines
WhatA nickname for your GitHub address.
WhyTyping the long URL every time would be painful.
HowSet it once with git remote add origin URL, then use git push origin main.
  • origin is just a nickname. Your GitHub address is long (https://github.com/USER/repo.git). Git lets you save it under a short name, like saving a phone number under a contact name. By convention that name is origin.
  • Who creates it? You, with git remote add origin URL, or Git itself when you run git clone.
  • Nothing magic: you could call it github or backup. Everyone just uses origin.
  • So git push origin main reads as: "send my main branch to the place nicknamed origin."
  • What is origin/main? Your PC's bookmark of where main was on GitHub the last time you talked to it. It updates only on fetch, pull or push.
YOUR PC GITHUB (origin) [ main ] ── git push origin main ──▶ [ main ] [ origin/main ] ◀──── git fetch / pull ───── (the real one)
git remote -v                       # list nicknames + URLs
git remote rename origin github     # change the nickname
git remote set-url origin NEW_URL   # same nickname, new address
git remote add upstream URL         # add a 2nd remote (e.g. a fork's original)

HEAD: the "You are here" pin

🧠 In 3 lines
WhatA pin showing where you are right now.
WhyGit needs to know which commit your next work builds on.
HowHEAD points to your branch; HEAD~1 means one commit back.
  • HEAD is Git's pointer to where you are working right now. Think of the red pin on a map.
  • Normally HEAD points to a branch (like main), and the branch points to its latest commit.
  • When you commit, the branch and HEAD move forward together. When you git checkout, HEAD jumps to another branch.
  • Detached HEAD = HEAD points straight at an old commit, not a branch (Module 15).
commits: A ──── B ──── C ▲ branch: main (a sticky note on C) ▲ HEAD ───────────────────┘ "I am on main, which is at C"
Written asMeans
HEADThe commit you are on now
HEAD~1 (or HEAD^)One commit before HEAD (its parent)
HEAD~3Three commits before HEAD
main~2Two commits before the tip of main

Module 6Git Basics: init, add, commit

🧠 In 3 lines
WhatGit saves work in three steps: edit, stage, commit.
WhyYou choose exactly what goes into each snapshot.
Howgit add moves changes to staging; git commit saves them.

The three areas

🧠 In 3 lines
WhatGit has three places a change passes through: working directory, staging area, repository.
WhyYou control exactly what goes into each commit.
Howadd moves forward to staging, commit saves it, reset HEAD file steps back.
Interactive map: tap any command. 🟠 orange = where data comes from, 🔵 blue = where it goes.
📝 Working Directoryfiles you edit
🛒 Staging Areanext commit's cart
🗄️ Local Repository.git history

Pick a command above to see exactly what it moves and what it leaves alone.

Travel table: every hop, both directions

Hop➡️ Forward⬅️ Backward
Working dir ↔ Staginggit add FILEgit reset HEAD FILE
Staging ↔ Local repogit commitgit reset --soft HEAD~1
Working dir ↔ Local repo (skip staging)git commit -am "msg"git reset --mixed HEAD~1 (keep files) or --hard (wipe)
Local repo ↔ Remotegit pushgit fetch (look) / git pull (apply)
Working dir ↔ Stashgit stash -ugit stash pop
Remote → everythinggit clone URL fills local repo and working dir in one go

Points to remember

  • Staging is a copy, not a move. After git add, your file is still in the working directory. If you edit it again, you must git add again.
  • Only staged changes get committed. Edits you didn't stage stay behind as "modified".
  • git status tells you the next move: red = working dir only, green = staged, clean = nothing to do.
  • Commits are local until pushed. Nobody on GitHub sees them yet.
  • Two kinds of "undo". Moving files between areas (safe: reset HEAD FILE, soft/mixed reset) vs deleting work (dangerous: checkout -- FILE, reset --hard).
  • Deleted a commit by accident? git reflog still remembers it for weeks.
mkdir git-practice && cd git-practice
git init                      # start tracking
git status                    # where is everything?

Working dir → Staging

echo "Hello" > hello.txt
# Stage one file. Edit it again? Add it again.
git add hello.txt
# Stage everything. Check git status first.
git add .
# Patch mode: asks per chunk. y=stage, n=skip, s=split, e=edit, q=quit.
git add -p

Staging → back to Working dir (unstage)

# Unstage: file leaves the cart, your edits stay.
git reset HEAD hello.txt

Throw away edits in Working dir

# Discard edits: back to last saved version. No undo.
git checkout -- hello.txt

Staging → Repository (commit)

git commit -m "Add hello.txt"
# -a stages tracked modified files, then commits (not new files).
git commit -am "Update"
# Replace the last commit. Only before pushing.
git commit --amend -m "New msg"

Inspect

# Unstaged changes (working vs staging).
git diff
# What the next commit will contain.
git diff --staged
git log --oneline --graph
Lifecycle: Untracked → Staged → Committed → Modified → Staged …
Try it: create a.txt and b.txt, stage only a.txt, run git status, unstage it, stage both, commit.

Module 8Git Push

🧠 In 3 lines
WhatSending your local commits up to GitHub.
WhyIt backs up your work and lets teammates see it.
Howgit push -u origin main the first time, then just git push.

Push uploads your local commits to the remote. Only commits travel. Edits you have not committed stay on your PC.

Read the command word by word

Part of git push -u origin mainPlain meaning
gitThe program.
pushAction: send my commits UP to a remote.
-uShort for --set-upstream: "remember this link." Afterwards, plain git push and git pull need no extra words.
originWhere to send: the nickname of your GitHub address (Module 5).
mainWhat to send: the branch called main.

Said in English: "Git, send my main branch to origin, and remember that these two are linked."

BEFORE push AFTER push your PC : A ─ B ─ C ─ D (main) your PC : A ─ B ─ C ─ D (main, origin/main) GitHub : A ─ B GitHub : A ─ B ─ C ─ D (status: "ahead by 2") (status: "up to date")
git push -u origin main                  # FIRST push of a branch: send it and remember the link
git push                                 # later pushes: send new commits of the current branch
git push origin feature-login            # push another branch by name (creates it on GitHub if new)
git push origin v1.0                     # push one tag (tags are NOT sent automatically)
git push origin --delete feature-login   # delete that branch on GitHub (your local copy stays)
git push --force-with-lease              # overwrite GitHub history ONLY if nobody pushed since you last looked
TermPlain meaning
upstreamThe remote branch your local branch is linked to (e.g. origin/main).
non-fast-forwardGitHub has commits you do not have. Git refuses so it does not erase them.
force pushOverwrites GitHub's history. Dangerous on shared branches. --force-with-lease is the safer version.
Push rejected? 1) git pull 2) fix any conflict 3) git push again.
Try it: commit something, run git status (ahead by 1), push, run git status again (up to date).

Module 9Git Fetch & Pull

🧠 In 3 lines
WhatBringing new work from GitHub down to your PC.
WhyYou stay up to date and avoid conflicts.
Howfetch only looks; pull downloads and updates your files.

Both bring new work from GitHub to your PC. The difference is whether your files change.

CommandDoesChanges your files?
git fetchDownloads new commits into the origin/main bookmark onlyNo (safe)
git pullfetch plus merge into your branchYes
GitHub ──fetch──▶ origin/main (bookmark) ──merge──▶ main (your branch) ──▶ your files └──────────────── git pull = both steps ────────────────────────┘
git fetch origin                        # origin = download from GitHub; nothing in your files changes
git log main..origin/main --oneline     # ".." = commits GitHub has that my main does not (what's new?)
git diff main origin/main               # show the actual line changes
git merge origin/main                   # now apply them to my branch
git pull                                # shortcut for fetch + merge
git pull --rebase                       # fetch + rebase: replay MY commits on top, straight history
Habit: git pull before you start work and before you push.

Module 15Git Checkout

🧠 In 3 lines
WhatMoving to another branch or to an old commit.
WhyYou can switch tasks and look at past versions.
Howgit checkout name, and come back with git checkout main.

One command, several jobs:

JobCommand
Switch to a branchgit checkout main
Create a branch and switchgit checkout -b new-branch
Discard edits in a filegit checkout -- file.txt
Visit an old commitgit checkout HASH
Get one file from an old commitgit checkout HASH -- file.txt

Detached HEAD: you're on a commit, not a branch. Keep new work with git checkout -b rescue; leave with git checkout main.

git checkout HASH -- file.txt   # restore one file from the past

Time travel: see old commits and come back (every step)

oldest ─────────────────────────────────▶ newest A ──── B ──── C ──── D ──── E ◀ main = the present ▲ git checkout B (you are visiting B) git checkout main (you are back at E)

Simple idea: history is a chain of snapshots. HEAD is "where you are standing". Visiting an old snapshot only moves HEAD. Nothing is deleted, and main stays safe at the present.

Step 1: Make your folder clean

git status        # want: "nothing to commit, working tree clean"
git stash -u      # only if you have unfinished edits: shelve them first

Step 2: See the list of old commits

git log --oneline                 # one line per commit, newest first. Space = next page, q = quit
# a1b2c3d Add search     <- newest (present)
# 9f8e7d6 Fix typo
# 5c4b3a2 Initial commit  <- oldest
git log --oneline --graph --all   # also draws branches
git log -5                        # last 5 only, full details
git log --since="2 days ago"      # by time
git log -- hello.txt              # history of one file

The 7-letter code (9f8e7d6) is the commit's hash, its ID. Copy it.

Step 3: Peek inside one commit (nothing changes yet)

git show 9f8e7d6          # message + exact lines changed in that commit
git show 9f8e7d6 --stat   # just which files changed
git diff 9f8e7d6 HEAD     # what changed between then and now

Step 4: Go there

git checkout 9f8e7d6   # your folder now shows that old version
git status                    # "HEAD detached at 9f8e7d6"

Git prints a "detached HEAD" notice. That is normal, not an error: it means you are on a commit, not on a branch. Your folder now looks exactly like it did then.

Step 5: Look around

Open files, run the app, read the code. Don't commit here unless you plan to keep it (see below).

Step 6: Come back to the present

git checkout main     # files jump back to the newest version
git status          # "On branch main"
git stash pop       # only if you stashed in Step 1

Lost your place? git checkout - returns to wherever you were before. git checkout main always works.

Extras

git checkout 9f8e7d6 -- hello.txt   # bring ONE old file into your folder, stay on main
git checkout HEAD -- hello.txt      # changed your mind: put it back
git checkout -b rescue                     # made commits while detached? run this BEFORE leaving to keep them
git reflog                               # forgot? find the hash here, then: git checkout -b rescue HASH

Shortcuts: HEAD = now, HEAD~1 = one commit before, HEAD~3 = three before. git show HEAD~2 works without knowing the hash.

GoalCommandChanges your files?
Browse historygit logNo
Inspect one commitgit show HASHNo
Visit the pastgit checkout HASHYes, until you switch back
Get one old filegit checkout HASH -- FILEOne file
Cancel a bad commit safelygit revert HASHNew commit
Move the branch backgit reset --hard HASHYes, dangerous
Try it: make 3 commits, run git log --oneline, visit the first with git checkout HASH, check your file, then git checkout main.

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

On GitHub: + → New repository → name task-tracker → Public (needed for free Pages later) → leave README unchecked → Create. Copy the URL (SSH or HTTPS, as set up in Module 5). Below, YOUR_REPO_URL means that URL.

Part B: Create the project and push it (Modules 6, 8, 10)

mkdir task-tracker && cd task-tracker
git init
cat > README.md << 'EOF'
# Task Tracker
A small to-do web app built to learn Git and GitHub.
EOF
cat > .gitignore << 'EOF'
node_modules/
.env
*.log
EOF
git status                        # both files are Untracked (red)
git add README.md .gitignore
git commit -m "Add README and .gitignore"
git remote add origin YOUR_REPO_URL
git remote -v                     # origin = nickname of your GitHub address
git push -u origin main

✅ Refresh GitHub: README appears.

Part C: Build the first page and practise staging (Module 6)

cat > index.html << 'EOF'
<!DOCTYPE html>
<html>
<head>
  <meta charset="utf-8">
  <title>Task Tracker</title>
  <link rel="stylesheet" href="style.css">
</head>
<body>
  <h1>Task Tracker</h1>
  <ul id="list"></ul>
  <script src="app.js"></script>
</body>
</html>
EOF
cat > style.css << 'EOF'
body { font-family: sans-serif; max-width: 480px; margin: 40px auto; }
li { padding: 6px 0; cursor: pointer; }
EOF
cat > app.js << 'EOF'
// Task Tracker app
const tasks = [];
const list = document.getElementById("list");

function render() {
  list.innerHTML = "";
  tasks.forEach(t => {
    const li = document.createElement("li");
    li.textContent = t.title;
    list.appendChild(li);
  });
}

function addTask(title) {
  tasks.push({ title: title, done: false });
  render();
}

addTask("Learn Git");
addTask("Push to GitHub");
EOF
echo "my private scribbles" > scratch.txt

C1. Working directory → Staging, then back out

git status                        # 4 untracked files
git add .                         # oops: this also staged scratch.txt
git status                        # scratch.txt is green (staged) by mistake
git reset HEAD scratch.txt  # staging → working dir; file kept
git status                        # scratch.txt is red/untracked again
git commit -m "Add basic page, styles and script"

C2. Ignore the junk file

echo "scratch.txt" >> .gitignore
git status                        # scratch.txt vanished; .gitignore is modified
git diff                          # shows the one added line (unstaged)
git add .gitignore
git diff --staged                 # what will be committed
git commit -m "Ignore scratch.txt"

C3. Discard a bad edit

echo "garbage" >> style.css
git diff                          # see the garbage
git checkout -- style.css             # discard it (no undo!)
git status                        # clean

C4. Stage only part of a file with add -p

sed -i '1s/.*/\/\/ Task Tracker app (v0.1)/' app.js
echo 'addTask("Deploy with Pages");' >> app.js
git add -p app.js                 # chunk 1 (comment): type y   chunk 2 (new task): type n
git diff --staged                 # only the comment change is staged
git commit -m "Add version comment"
git commit -am "Add deploy task"  # -a stages the remaining tracked change
git log --oneline
git push

Part D: First feature through a Pull Request (Modules 11, 12, 8, 9)

Strategy: GitHub Flow. One short-lived branch per feature, then a Pull Request.

git checkout -b feature/mark-done
sed -i 's|    li.textContent = t.title;|    li.textContent = t.title;\n    li.onclick = () => { t.done = !t.done; render(); };\n    if (t.done) li.className = "done";|' app.js
echo ".done { text-decoration: line-through; color: gray; }" >> style.css
git diff                          # review before committing
git commit -am "Click a task to mark it done"
git push -u origin feature/mark-done

On GitHub: Compare & pull request → Create pull request → Merge pull request (choose a normal merge commit) → Delete branch. Then bring it down:

git checkout main
git pull                          # main now has the feature
git branch -d feature/mark-done   # delete the local copy
git branch -a                     # list local + remote branches

Part E: A teammate joins, and you collide (Modules 7, 9, 13)

E1. You start a change but do not push yet

git checkout -b feature/my-title
sed -i 's|<h1>Task Tracker</h1>|<h1>My Task Tracker</h1>|' index.html
git commit -am "Rename heading to My Task Tracker"

E2. Teammate (open a second Git Bash window)

cd ..
git clone YOUR_REPO_URL task-tracker-teammate     # full copy; origin is set automatically
cd task-tracker-teammate
git config user.name "Teammate"                   # --local: only for this repo
git config user.email "teammate@example.com"
git checkout -b feature/team-title
sed -i 's|<h1>Task Tracker</h1>|<h1>Team Task Tracker</h1>|' index.html
git commit -am "Rename heading to Team Task Tracker"
git push -u origin feature/team-title

On GitHub, open and merge the teammate's Pull Request. You and the teammate changed the same line.

E3. Back in your window: fetch, look, pull, merge

cd ../task-tracker
git fetch                              # download only, files untouched
git log --oneline main..origin/main    # what is new on GitHub?
git diff main origin/main              # the exact changes
git checkout main
git pull                               # main is updated
git checkout feature/my-title
git merge main                         # CONFLICT in index.html
git status                             # "both modified: index.html"

Open index.html. Replace the marker block with one final line, e.g. <h1>My Team Task Tracker</h1>, and delete the lines <<<<<<<, =======, >>>>>>>.

git add index.html
git commit --no-edit                   # finishes the merge
git push -u origin feature/my-title

GitHub: create the PR, merge it, delete the branch. Then git checkout main && git pull && git branch -d feature/my-title.

Part F: Urgent bug while you are mid-feature (Module 14)

git checkout -b feature/clear-done
cat >> app.js << 'EOF'

function clearDone() {
  for (let i = tasks.length - 1; i >= 0; i--) {
    if (tasks[i].done) tasks.splice(i, 1);
  }
  render();
}
EOF
echo "idea: add a Clear button" > clear-notes.txt
git status                             # 1 modified + 1 untracked: unfinished work
git stash push -u -m "wip clearDone"   # shelve both
git status                             # clean
git stash list

Boss: "The page title needs fixing now!" Use a hotfix branch:

git checkout main
git checkout -b hotfix/page-title
sed -i 's#<title>Task Tracker</title>#<title>Task Tracker - Learn Git</title>#' index.html
git commit -am "Fix page title"
git push -u origin hotfix/page-title   # merge the PR on GitHub
git checkout main
git pull
git branch -d hotfix/page-title
git checkout feature/clear-done
git stash pop                          # your unfinished work is back
git stash list                         # empty

Part G: Make mistakes and undo them (Module 16)

You are on feature/clear-done. Each step is a realistic slip-up.

G1. Typo in the commit message → amend

git add app.js
git commit -m "Add clearDone fucntion"
git commit --amend -m "Add clearDone function"
rm clear-notes.txt

G2. Two unrelated changes in one commit → mixed reset

sed -i 's|  <script src="app.js"></script>|  <button onclick="clearDone()">Clear done</button>\n  <script src="app.js"></script>|' index.html
echo "button { padding: 6px 12px; }" >> style.css
git commit -am "Add button and styles"
git reset HEAD~1                       # commit undone, both files unstaged
git status
git add index.html && git commit -m "Add Clear done button"
git add style.css  && git commit -m "Style buttons"

G3. Bad commit message → soft reset

sed -i 's|</body>|  <footer>Built with Git</footer>\n</body>|' index.html
git commit -am "stuff"
git reset --soft HEAD~1                # commit undone, change still STAGED
git status
git commit -m "Add footer"

G4. Bad experiment → hard reset, then rescue with reflog

echo "body { background: hotpink; }" >> style.css
git commit -am "Experiment: hotpink"
git reset --hard HEAD~1                # commit AND change are gone
git reflog                             # find the hash next to "Experiment: hotpink"
git reset --hard HASH_FROM_REFLOG      # it is back!
git reset --hard HEAD~1                # now drop it on purpose

G5. Bad commit already pushed → revert (safe for shared history)

git push -u origin feature/clear-done
echo "tasks.length = 0;" >> app.js
git commit -am "Quick tweak"
git push
git revert --no-edit HEAD              # new commit that undoes the tweak
git push

Part H: Look at the past and come back (Module 15)

git log --oneline                      # pick a hash a few commits back
git show HEAD~2 --stat                 # which files that commit touched
git diff HEAD~4 HEAD --stat            # now vs 4 commits ago
git checkout HEAD~4             # visit the past (detached HEAD)
cat index.html                         # the page as it was then
git checkout feature/clear-done          # back to the present
git checkout HEAD~4 -- style.css  # grab ONE old file
git diff --staged                               # the old file is now staged
git checkout HEAD -- style.css                  # put the newest version back

Part I: Tidy the history with rebase (Module 17)

git checkout main
git pull
git checkout feature/clear-done
git rebase main                        # replay your commits on top of the latest main
git rebase -i main                     # editor opens

In the editor keep the first line as pick and change every other pick to squash. Save and close. In the next editor, write one message: Add Clear done feature. Save and close.

git log --oneline                      # your 6 messy commits are now 1
git push --force-with-lease            # history was rewritten; safe on YOUR OWN branch only

GitHub: create the PR, merge it (normal merge commit), delete the branch.

Part J: Release and go live (Modules 8, 9)

git checkout main
git pull
git branch -d feature/clear-done
git fetch --prune                      # forget deleted remote branches
git tag -a v1.0 -m "First release"
git push origin v1.0
git log --oneline --graph --all        # admire the whole story

Publish the site: GitHub repo → Settings → Pages → Source: Deploy from a branch → main / (root) → Save. After about a minute your app is live at https://USERNAME.github.io/task-tracker/. Then Releases → Draft a new release → choose tag v1.0 → Publish.
